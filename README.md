# 図面AR（試作）

追跡制御修正：2026-10-09。利用者から実機で安定性が向上したとの報告あり。
今回の追加変更：画像の縦横ピクセル数を認識データから自動取得。実寸の縦横入力と確認用数値表示は維持。
追加変更後の実機動作は未確認です。
変更点・検証結果・スマホでの確認手順は `UPDATE_NOTES.md` を参照してください。
Blenderでの配置・書き出し・台帳の設定方法は `ALIGNMENT_DESIGN.md` を参照してください。

紙の図面にスマホをかざすと、対応する3Dモデル・資料情報・アノテーションが出る静的サイト。
サーバー処理なし。ライブラリはすべて `lib/` に同梱し、外部への通信はしない。

ARでは図面に対するモデルの配置を閲覧者が変更しない。スマホの移動には追従するが、
指での回転・拡大縮小は行わない。画像左下＝Blender原点、右＝＋X、上＝＋Y、紙面から上＝＋Z。
ARではモデルの中心や外寸による配置調整を行わず、制作時の座標を保持する。
画像外周に枠線は不要。内側の図柄で認識し、元画像全体の左下と入力寸法を配置基準にする。

## 実寸の入力

`data/items.json` の各資料の `target` 内に、画像全体に対応する実寸の幅・高さをm単位で記入する。

```json
"realWidthM": 40.0,
"realHeightM": 30.0
```

上は横40m・縦30mの例。印刷した紙の大きさや、図柄だけの寸法ではなく、余白を含む画像全体の値を入力する。
Blenderも同じ実寸・m単位・左下原点で配置する。縦横とも必須で、旧 `blenderWidth` は使用しない。
同梱の1m×約0.670276mは試験用の仮寸法なので、実際の値に書き換える。
画像の縦横ピクセル数は `all.mind` から自動取得する。`widthPx`・`heightPx` の入力は不要で、旧値が残っていても無視する。
認識データ内の画像と入力実寸の縦横比が1%を超えて違うと、AR起動画面にエラーを表示する。
1%以内の丸め差は許容し、モデルのXYZへ横幅基準の共通倍率を使う。

## 構成

```
index.html          一覧（QRの飛び先にもできる）
ar.html             AR表示（?id=資料ID を付けるとそのモデルを先読みする）
viewer.html         通常の3D表示（認識できないとき・カメラが使えないときの逃げ先）
tools/              管理用：認識用データの作成、QRコード
data/items.json     台帳（図面1枚＝1件）
data/<id>/          model.glb / meta.json / annotations.json
targets/all.mind    認識用データ（全図面をまとめた1ファイル）
targets/src/        認識用データの元になる図面画像
lib/ js/ css/       同梱ライブラリと本体
```

本体のうち追跡に関わるもの：`js/tracking.js`（MindAR の追跡処理の差し替え）、
`js/oblique.js`（斜めから見た図面を探すための計算）、
`js/stabilizer.js`（表示の揺れ止めと、見失ったときの固定表示）、
`tools/trackpoints.js`（追跡用の手がかりの選び直し）。

## 公開（GitHub Pages）

1. このフォルダの中身をリポジトリの最上位に置いて push する。
2. Settings → Pages → Branch を `main` / `(root)` にする。
3. `https://<ユーザー名>.github.io/<リポジトリ名>/` で開く。

カメラは HTTPS でしか動かない。PCでの確認は、このフォルダで `python -m http.server` を実行し
`http://localhost:8000/` を開く。スマホ実機での確認は Pages に上げてから行う。

`targets/src/` の図面画像は認識用データを作るときにだけ使い、公開サイトの表示には使わない。
権利の確認が取れていない図版は、リポジトリに入れずに手元だけに置く。

## 図面を追加する

1. `ALIGNMENT_DESIGN.md` に従って図面左下をBlender原点に置き、モデルを合わせてGLBを書き出す。
   モデルを軽くする場合も、その配置を保つ（目安：テクスチャ 2048px 以下、5MB 前後）。
   `npx @gltf-transform/cli resize in.glb a.glb --width 2048 --height 2048`
   `npx @gltf-transform/cli draco a.glb model.glb`
2. `data/<id>/` に `model.glb`、`meta.json`、`annotations.json` を置く。
3. 図面画像を `targets/src/<id>.jpg` に置く。**印刷するものと同じ画像**を使う。
4. `data/items.json` に1件足す。画像全体の `realWidthM`・`realHeightM` とモデルの `coordinateSystem` を記録する。
   `targetIndex` は 0 から順に重複なく振る。
5. `tools/` を開き「作成する」→ 保存した `all.mind` を `targets/all.mind` に置き換える。
6. 同じページでQRコードを作り、図面に添えて印刷する。

印刷後に変えられないもの：公開URL（QRに入る）と図面画像（変えると配布済みの紙が反応しなくなる）。

## 画像を差し替える

1. `targets/src/item01.jpg`（または台帳の `target.source`）を新しい画像に置き換え、公開への反映を待つ。
2. 画像全体が表す実寸が変わる場合は、`data/items.json` の `realWidthM`・`realHeightM` を更新する。解像度の入力は不要。
3. 管理用ページ `tools/` で「作成する」→「all.mind を保存」を押す。
4. 保存したファイルで `targets/all.mind` を置き換え、公開への反映を待ってARページを開き直す。

JPGだけの差し替えでは、認識対象は変わらない。実寸だけの変更なら `all.mind` の再作成は不要。
管理用の画像取得とAR起動時の認識データ取得は、ブラウザのキャッシュを再検証する。
ARの起動中は、配置計算と追跡に同じ認識データを使用する。「探し直す」でも同じデータを使うため、
公開ファイルの差し替えを反映する際はARページを開き直す。

## 既存サイトへの今回の更新

`ar.html`・`viewer.html`・`js/`・`tools/` を上書きする。
実データを設定済みの場合は、`data/` と `targets/` は現在のものを使い、同梱の試験データで上書きしない。
既存の `data/items.json` に `widthPx`・`heightPx` が残っていても削除は必須ではない。
画像を変更していなければ、このプログラム更新だけのために `all.mind` を作り直す必要はない。

## 台帳（data/items.json）

| 項目 | 内容 |
|---|---|
| `id` | 資料ID。URLとフォルダ名に使う |
| `targetIndex` | `all.mind` の中での順番（0始まり） |
| `target.source` | 図面画像の場所 |
| `target.realWidthM` | 画像全体の実寸幅（m）。必須。Blenderの図面幅もこの値にする |
| `target.realHeightM` | 画像全体の実寸高さ（m）。必須。Blenderの図面高さもこの値にする |
| `model.src` | モデルの場所 |
| `model.coordinateSystem` | 標準の＋Y Up GLBは `gltf-y-up`（既定）。＋Z Upのまま保存したGLBは `blender-z-up` |
| `model.rotationDeg` | 旧データ向けの通常ビュー専用補正。ARでは使用しない |
| `meta` / `annotations` | それぞれのJSONの場所（省略可） |

`site.title` と `site.lead` は一覧の見出し。

旧 `display.mode`、`display.anchor`、`display.size`、`target.printWidthMm`、`target.blenderWidth`、`model.metersPerUnit` はAR配置に使用しない。
同梱の試験用GLBは＋Z Upで、左下原点に合わせ直したデータではない。負の座標もそのまま表示される。
新しい標準GLBへ差し替えるときは `model.coordinateSystem` を `gltf-y-up` に変更する。

## 追跡の調整

モデルが揺れる・消えるときは、カメラ起動画面の「確認用の数値を表示」にチェックを入れる。
URLを変える必要はない。従来の `ar.html?debug=1` も使える。
「画像寸法 自動取得（all.mind）」と出れば、今回の変更が読み込まれている。図面認識後に、その図面の縦横ピクセル数が表示される。

| 表示 | 見方 |
|---|---|
| 画像寸法 自動取得（all.mind） | 認識に使用している画像全体の縦横ピクセル数。JSONの旧入力値は使わない |
| 図面全体 幅×高さ / 軸 | 入力した実寸幅・高さ（m）と、GLBの座標設定 |
| 縦横比差 | 画像と入力実寸の縦横比の差。1%以内の丸め差は許容 |
| モデル範囲 X / Y / Z | Blender座標でモデルの形状が占める範囲。負の値がある場合もアプリは移動・切り詰めしない |
| 認識 n回/秒 | 追跡処理の速さ。10を下回ると動きに追いつけず見失いやすい |
| 手がかり n点 → 採用 m点 / 必要 6点 | 目印の一致数と、食い違う点を除外したあとの採用数。開始・継続とも採用6点以上が必要 |
| 最終姿勢から n ms | 最後に追跡姿勢が届いてからの時間。数値が増え続ける間は姿勢が更新されていない |
| 発見 | 図面を探して見つけた回数 |
| 探索 正面 a/b 傾50 a/b … | 探し方ごとの成功回数／試した回数。正面＝MindAR既定、傾50・傾65＝その傾きを仮定、前回＝最後に追跡できた向きを仮定。どれも b ばかり増えるなら、探す段階でつまずいている |
| 却下 | 見つけた直後に追跡へ移れず、探し直した回数 |
| 探し直し / 見失い | 追跡をあきらめて図面を探し直した回数／表示を固定に切り替えた回数 |
| 作り直し | 処理停止を検知して、旧Workerを終了し、カメラと追跡を自動で作り直した回数 |
| エラー | 追跡の処理で出た例外の数と、最後の内容 |
| 映像 | カメラ映像の画素数 |

設定は台帳の最上位に `"tracking": { ... }` を足すと変えられる。同じ名前をURLに付けて
試すこともできる（例 `ar.html?debug=1&stillCutoff=0.3`）。

| 項目 | 既定 | 内容 |
|---|---|---|
| `stillCutoff` | 0.5 | 手を止めているときの揺れ止めの強さ。小さいほど揺れないが、動き出しが遅れる |
| `posFollow` / `rotFollow` | 15 / 7 | 動かしたときに追従を速める度合い（位置／向き）。大きいほど遅れないが揺れが残る |
| `hold` | 1 | 1＝見失っても最後の姿勢で表示を残す。0＝消す |
| `lostAfterMs` | 800 | 姿勢が得られない状態が何ミリ秒続いたら「見失った」とするか |
| `minPoints` | 6 | 姿勢の更新に使う手がかりの最少数 |
| `retryAfterMs` | 300 | 最後に追跡できてから、この時間を超えて失敗が続くと探し直す。実行は次の処理コマになるため端末の速度による遅れは残る |
| `rejectOutliers` | 1 | 1＝周りと食い違う手がかりを姿勢の計算から外す |
| `obliqueSearch` | 1 | 1＝斜めから見た図面も探す |
| `searchTilts` | [50, 65] | 斜めの探索で仮定する傾き（度）。図面の奥側が画面の上に来る向き。机の上の図面を想定 |
| `searchSideTilts` | [] | 同上、奥側が画面の左右に来る向き。壁に貼った図面を横から見る場合に `[50]` などを入れる |
| `warmupTolerance` | 2 | 表示を始めるまでに必要な連続成功コマ数 |
| `cameraLongSide` | 0 | カメラ映像の長辺の希望画素数（0＝ブラウザ任せ）。実機では未確認 |

以前の `retryFrames` は使用しない。既存設定がある場合は `retryAfterMs`（ミリ秒）へ置き換える。
大きな姿勢変化は、新しい近い向きの観測が3回以上、250ms以上にわたり続いた場合に採用する。
同じ観測の再描画は回数に数えず、途中で観測が500msを超えて途切れた場合は確認をやり直す。

### 見失ったとき

画面に「図面を見失いました」と出ている間、モデルは最後の位置のまま画面に残る。
図面を画面いっぱいに映し直すと自動で追跡に戻る。戻らないときは「探し直す」を押すと、
カメラと追跡を作り直す（ページの再読み込みは不要）。

以下の成功率・角度の記述は旧版READMEからの参考値で、この修正での再測定値やスマホ実測値ではない。
図面は近いほど見つけやすい。擬似映像での1回あたりの成功率は、図面が画面からはみ出す近さで約9割、
画面幅の8割で約6割、画面幅の半分で約3割だった。

### 斜めから見たとき

MindAR 既定の探し方は正面に近い見え方が前提で、傾き（真上から見たときを0°とする）が45°で成功率2割、
55°以上ではほぼ0になる。そこで、映像を「図面と正対したらこう見える」形に直してから探す方法を
1コマおきに挟んでいる。傾きは事前にわからないので、50°と65°を仮定して順に試し、
一度追跡できたあとは、そのときの向きも候補に加える。

擬似映像では、傾き45〜65°で、仮定が合った回はほぼ毎回見つかった。72°では見つかるが、
その後の追跡が続かない（手がかりが4点前後しか合わない）。実用になるのは65°くらいまで。

## 資料情報（meta.json）

```json
{ "title": "表示名", "fields": [ { "label": "遺跡名", "value": "" } ], "notice": "" }
```

`value` が空の項目は画面に出ない。

## アノテーション（annotations.json）

レイヤー単位で `uid`・`Annotation_Type`（Point / Line / Area）・`metadata` を持つ。
座標は **GLBを読み込んだときの座標**（`rotationDeg` をかける前）。

```json
{
  "coordinate": "glb",
  "layers": [
    { "uid": "…", "name": "Point_001", "Annotation_Type": "Point", "color": "#ff3b30",
      "metadata": { "内容": "…" },
      "items": [ { "label": "1", "note": "…", "position": [x, y, z] } ] },
    { "uid": "…", "name": "Line_001", "Annotation_Type": "Line",
      "items": [ { "points": [[x, y, z], [x, y, z]] } ] },
    { "uid": "…", "name": "Area_001", "Annotation_Type": "Area",
      "items": [ { "points": [[x, y, z], [x, y, z], [x, y, z]] } ] }
  ]
}
```

Area は境界線だけを描き、終点から始点へ自動で閉じる（面の塗りは未対応）。

## 制限

- iPhone は iOS 16.4 以降の Safari。LINE や X のアプリ内ブラウザではカメラが動かないことがある。
- 白地に細い線だけの図面は認識できない。`tools/` の「追跡用」の数で事前に確かめる。
- 揺れ止めのため、端末を速く動かすとモデルが図面より少し遅れて動く。
- 図面が画面から外れるとモデルは画面上で固定される（図面を画面いっぱいに映し直すと追跡に復帰する）。
- 斜めから見られるのは傾き65°くらいまで。それより寝かせた角度では追跡が続かない。
- 同時に追う図面は1枚。読み込んだモデルは2件まで保持し、古いものから捨てる。
